# Stockage objet Cloudflare R2

Par defaut, le lac de donnees brut vit sur le disque local (et, sur la
version publique, etait committe dans git). A l'echelle - zone monde, haute
frequence, plusieurs sources - git n'est plus adapte : il grossit trop vite.

**Cloudflare R2** est un stockage objet compatible S3, gratuit jusqu'a 10 Go,
**sans frais de sortie**. Une fois configure, le lac brut vit sur R2 ; dbt le
lit en `s3://`, et le depot git reste leger. L'entrepot DuckDB, lui, reste
local (reconstruit depuis R2).

Rien d'autre ne change dans le code : renseigner les identifiants R2 suffit a
basculer tout le pipeline.

---

## 1. Creer le bucket et le jeton (cote Cloudflare)

1. Creer un compte sur [dash.cloudflare.com](https://dash.cloudflare.com) (gratuit).
2. Dans le menu, ouvrir **R2**. Cloudflare peut demander une carte pour activer
   R2 : le palier gratuit (10 Go, pas de frais de sortie) ne debite rien tant
   qu'on reste sous les limites - ce projet en est tres loin.
3. **Create bucket** -> nom par exemple `skytrace-lake` -> region *Automatic*.
4. Recuperer l'**Account ID** : il est affiche sur la page R2 (et dans l'URL du
   tableau de bord). C'est aussi le debut de l'endpoint S3
   `<account_id>.r2.cloudflarestorage.com`.
5. Creer un jeton d'acces : **R2 -> Manage R2 API Tokens -> Create API Token**
   -> permission **Object Read & Write** -> (optionnel) restreindre au bucket.
   Cloudflare affiche alors, **une seule fois** :
   - **Access Key ID**
   - **Secret Access Key**

   Note-les tout de suite.

Tu as maintenant quatre valeurs :

| Variable | Ou la trouver |
|---|---|
| `SKYTRACE_R2_ACCOUNT_ID` | page R2 (Account ID) |
| `SKYTRACE_R2_BUCKET` | le nom du bucket (`skytrace-lake`) |
| `SKYTRACE_R2_ACCESS_KEY_ID` | jeton API cree |
| `SKYTRACE_R2_SECRET_ACCESS_KEY` | jeton API cree |

---

## 2. Tester en local

Renseigner les quatre valeurs dans `.env` (copie de `.env.example`), puis :

```bash
skytrace storage-check
```

La commande ecrit puis relit un petit objet temoin. Elle doit afficher
`Acces au lac OK (R2)`. Si elle echoue, le message indique la cause
(identifiants, endpoint, permission du jeton).

Ensuite, une vraie collecte vers R2 :

```bash
skytrace pipeline
```

Le snapshot est ecrit sur R2, dbt le relit en `s3://`, le tableau de bord
l'affiche. `skytrace dashboard` fonctionne a l'identique.

---

## 3. Brancher le collecteur (GitHub Actions)

Dans le depot GitHub : **Settings -> Secrets and variables -> Actions ->
New repository secret**, ajouter les quatre secrets :

- `SKYTRACE_R2_ACCOUNT_ID`
- `SKYTRACE_R2_BUCKET`
- `SKYTRACE_R2_ACCESS_KEY_ID`
- `SKYTRACE_R2_SECRET_ACCESS_KEY`

Le workflow *Collecte planifiee* les utilise deja : il verifie l'acces R2,
collecte vers R2, et ne committe plus aucune donnee dans git.

---

## 4. Brancher le tableau de bord (Streamlit Cloud)

Dans l'application Streamlit : **Settings -> Secrets**, coller au format TOML :

```toml
SKYTRACE_R2_ACCOUNT_ID = "..."
SKYTRACE_R2_BUCKET = "skytrace-lake"
SKYTRACE_R2_ACCESS_KEY_ID = "..."
SKYTRACE_R2_SECRET_ACCESS_KEY = "..."
```

Le tableau de bord reconstruit alors l'entrepot depuis R2 au demarrage, puis
le rafraichit periodiquement (toutes les 10 minutes) pour capter les
nouvelles donnees - sans redeploiement, puisqu'en mode R2 le collecteur
n'ecrit plus dans git.

---

## Ce que R2 debloque

Une fois R2 en place, on peut sans risque :

- passer la zone au **monde** (`SKYTRACE_REGION=world`) ;
- **accelerer** la cadence de collecte ;
- inclure **plus d'aeroports**.

Le depot git ne bouge plus ; seul R2 grossit, et 10 Go representent des mois
de collecte mondiale.
